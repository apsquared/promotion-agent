# Release and live-use checklist

Promotion-agent is an interactive skill/command plus local Node helpers. “Live” means a founder can install it into an explicitly selected product checkout, invoke it in their existing agent session, and get a useful reviewed draft. There is no web server or hosted deployment in this plan.

## Verified locally on 2026-09-27

- `npm run check` passed: TypeScript typecheck, build, and 55/55 tests.
- `npm pack --pack-destination /private/tmp --json` produced a 30-file `promotion-agent-0.0.0.tgz` containing compiled JavaScript, four user-facing docs, templates, README and MIT license; no source TypeScript, internal plan/handoff, or `node_modules` was packed.
- An offline `npm install --prefix <temporary-directory> --ignore-scripts` of that tarball succeeded. The installed binary onboarded a fictional project, inspected a valid empty task snapshot, removed 31 unchanged managed files with a reviewed plan, kept product configuration and tasks, and reinstalled the skill. This was an isolated install on the current machine, not a second clean OS image.
- The tested host was macOS 14.5 arm64, Node v22.14.0, npm 10.9.2. The package declares Node >=22.14.0. Linux, Windows and newer Node versions have not been exercised here.
- Upgrade tests cover idempotence, updating an unchanged workflow from a newer compiled bundle, and preserving locally edited workflow/configuration. Removal tests cover stale-plan rejection, customized wrapper preservation, product-data preservation and reinstall. Empty directories and a manifest for retained product files may remain after removal; inspect before manual cleanup.
- The repo has an MIT LICENSE and `license: MIT` package metadata. The extraction record is in `docs/EXTRACTION.md`; public source location and release provenance still need an actual remote/release workflow.
- A 1280×640, 153 KB `assets/opengraph.png` was added for the repository preview. The subsequent `npm pack --dry-run --json` passed with 31 files, including the image; the earlier 30-file offline-install test preceded this asset addition.

These checks validate files and deterministic helpers. They do **not** establish native invocation in all three agents, an outside founder's result, public registry availability, or external publishing.

## Remaining gates to “published and live”

1. **Choose the public identity and source repository.** Confirm the npm package name/scope and public Git remote. This checkout has no Git remote. Set `repository`, `homepage` and `bugs` to the real public URLs; choose an initial nonzero release version. Check npm name availability immediately before publishing. Update the README for package consumers and verify every relative documentation link from the packed package or public repository. Keep the package private until the release decision.
2. **Run host-native acceptance on a fictional checkout.** In a fresh interactive Codex session, select `$promotion-agent`; in Claude Code and OpenCode, select `/promote`. For each host, confirm the menu entry appears, the shared workflow is read, `inspect`/`prepare` work on the selected project, and a draft is shown for exact-content review without launching another AI CLI. Record host version, OS, date, invocation and artifact. Static wrapper files and the current Codex skill catalog are insufficient evidence. [Codex skills](https://learn.chatgpt.com/docs/build-skills), [Claude Code skills and compatible command files](https://code.claude.com/docs/en/skills), and [OpenCode commands](https://opencode.ai/v2/docs/commands) document the expected entry-point layouts.
3. **Run an outside-founder trial.** Give a founder who did not build the tool the release tarball and one explicitly selected product checkout. Ask them to onboard it with the reviewed plan, invoke their preferred agent natively, and produce one useful draft for a real marketing task. Capture their feedback, the draft path, what facts were used, any missing-tool fallback, and whether the draft was actually reviewable. Do not treat the internal P05 fictional artifacts as this trial.
4. **Broaden compatibility before claiming broad OS support.** Repeat pack/install/onboard/invoke/remove on the host/OS versions you intend to advertise, including Linux and Windows if they are in scope. Test the minimum declared Node version and the actual current host versions. Narrow the support statement if only macOS is verified.
5. **Prepare a release commit.** Review the full diff and package contents for secrets, customer data, machine-specific paths and unrelated edits. Commit only intended repository paths, run `npm ci && npm run check`, `npm pack --dry-run --json`, skill validation and `git diff --check` on the release commit. Configure CI for the supported OS/Node matrix. Back up any private product data separately; it is not part of this package.
6. **Publish source and package as separate authorized actions.** Push the reviewed commit/tag to the chosen remote. After npm identity, access and release version are set, remove `private: true` and publish the exact reviewed tarball or commit. Use a trusted publishing/provenance workflow if configured; otherwise record the build commit and tarball integrity in the release notes. npm will not publish a package marked private, and a published name/version cannot be reused. See [npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish/) and [package metadata](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/).
7. **Verify public use after publication.** From a fresh external checkout, install the public package by its exact name/version, repeat onboarding and native invocation, and compare the downloaded package integrity with the reviewed release. Confirm the public README, license, source tag, upgrade and removal instructions resolve. Then call it published/live; record any remaining host limitations in `docs/COMPATIBILITY.md`.

For the repository link preview, upload `assets/opengraph.png` in GitHub **Settings → Social preview → Edit → Upload an image** after the public repository exists. The 1280×640 PNG is under 1 MB; committing or embedding it in the README alone does not configure GitHub's social preview. See [GitHub's social preview instructions](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview).

No npm publish, remote push, real product installation, external post, or spending occurred during P07 local verification.

## Local upgrade and removal

From a newer installed package or checkout outside the selected product, run `promotion-agent onboard --project <product> --name <display-name> --plan <private-new-plan.json>`, review the plan and apply with `promotion-agent install --project <product> --plan <private-new-plan.json> --review-hash <printed-hash>`. Only unchanged managed files update; locally edited and product-owned files remain.

For removal, run `promotion-agent remove-preview --project <product> --plan <private-new-plan.json>`, inspect the paths, then `promotion-agent remove --project <product> --plan <private-new-plan.json> --review-hash <printed-hash>`. The plan file contains before-images and an absolute selected path; keep it private. Removal deletes only unchanged installer-owned runtime/wrappers, preserving custom files, product configuration, marketing facts/tasks/logs, and any optional local SQLite registry. Use the package or checkout outside the product so the running helper does not delete its own code while executing.
